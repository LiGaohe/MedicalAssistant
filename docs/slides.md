# 研究背景与目标

### 研究背景

- 门诊医生需边问诊边记录病历
- 注意力分散，问诊效率下降
- 医疗场景对术语准确性要求高
- 患者口语化表达，医生专业术语混杂

### 研究目标

- 将医患录音自动转写为对话文本
- 从对话中抽取病历要素
- 将口语化表达纠正为标准医学术语
- 生成结构化病历（SOAP格式）

::right::

### 核心问题

- 提高关键术语的识别率
- 将ASR错词映射到标准医学术语
- 抑制幻觉，减少关键事实遗漏
- 设计适合工程实现的实验方案

<!--

基于这样的背景，我们的研究目标是将医患对话的语音自动转成结构化病历。具体来说，这个目标可以分为四个步骤：首先是录音转写为对话文本，其次是从对话中抽取病历要素，然后是将口语化表达纠正为标准医学术语，最后是生成结构化病历。

针对医患对话场景，为了实现目标，面临4个主要问题。一个是门诊对话中充斥着大量专业术语。若ASR无法准确识别这些术语，后续的信息抽取和病历生成就失去了准确的基础。因此，提升术语识别率是实现高精度转写和后续精准抽取的前提；第二，即使采用定制化ASR，转写文本仍可能存在错误，尤其是低频或发音相似的术语。这些错误必须被纠正。因此，我们需要将ASR输出的错误医学词汇，准确映射到标准医学术语；另外，在实现术语标准化和生成最终病历时，我们引入了大模型，是存在"幻觉"风险的。在医疗场景下，这是不可接受的。因此，必须设计机制来杜绝幻觉；最后为了确保系统可以落地部署，需要考虑如何设计适合工程实现的实验方案。

# 调研：国内外研究现状

### 端到端病历生成

- SOAP note生成：模块化摘要更稳健
- MIE、SAFE：医疗对话信息抽取
- EMRModel：对话映射到结构化病历模板
- 重点在抽取与生成，术语纠错讨论不足

::right::

### 医疗ASR与术语纠错

- ASR-EC Benchmark：大模型纠错效果有限
- Post-decoder biasing：加权词表增强识别
- DiCODER：词典检索+拼音相似性+受控解码
- 低频术语识别是系统成败的前置条件

<Block type="info">

**现有研究的不足**：中文门诊录音到标准病历的完整系统研究相对分散，模块之间常分别优化，缺少围绕术语准确性的统一设计。

</Block>

<!--
在调研阶段，我研究了国内外相关文献。端到端病历生成方面，SOAP note生成表明模块化摘要更稳健，MIE、SAFE等工作主要聚焦于医疗对话信息抽取，EMRModel展示了将对话映射到结构化病历模板的可行性。但这些工作重点在抽取与生成，对术语纠错讨论不足。

医疗ASR方面，ASR-EC Benchmark证明大模型纠错效果有限，Post-decoder biasing通过加权词表增强识别，DiCODER说明词典检索、拼音相似性和受控解码可以减少低频实体误改。

# 架构细化：分层架构设计

<div class="flex justify-center my-2">
<img src="./system-architecture.svg" alt="系统架构图" class="max-w-md w-full">

### 架构层次

- **输入层**：ASR模块、原始文本
- **处理层**：证据选择、术语规范化、结构化生成、验证
- **输出层**：结构化病历

::right::

### 设计原则

- 事实来源单一：对话文本为唯一事实来源
- 分层处理：证据选择 → 术语规范化 → 结构化生成 → 验证
- 受控术语增强：术语规范化作为受控的第二步

<Block type="info">

**架构优势**：职责清晰，每层独立，可单独优化某一层，便于后续扩展。

</Block>

# 系统设计：ASR模块架构

### 设计模式

- 工厂模式 + 策略模式
- ASRBase定义统一接口
- 具体引擎实现转写逻辑
- ASRFactory统一管理创建

### 设计原则

- 单一职责：每个引擎专注一种模型
- 开闭原则：扩展无需修改现有代码
- 依赖倒置：依赖抽象接口

::right::

### 扩展性优势

- 继承ASRBase实现新引擎
- 通过Factory注册
- 修改配置即可切换
- 便于技术选型验证

<Block type="info">

**为什么这样设计？**

ASR技术发展迅速，需要能够快速切换引擎对比效果。工厂模式使得后续接入Whisper或Qwen3 ASR时，只需实现接口并注册，无需修改业务代码。

</Block>

<!--

这样做的好处是符合开闭原则，扩展新引擎无需修改现有代码。为什么这样设计？因为ASR技术发展迅速，需要能够快速切换引擎对比效果。后续如果要接入Whisper或Qwen3 ASR，只需继承ASRBase实现接口，通过Factory注册，修改配置即可切换，无需修改业务代码。

# ASR技术选型：对比权衡

| 对比维度 | FunASR | Qwen3 ASR | Whisper |
|----------|--------|-----------|---------|
| 中文识别准确率 | AISHELL-1: 1.95% | AISHELL-2: 2.71% | zh WER: ~13.8% |
| 流程完整性 | VAD + 标点 + 热词 + 说话人分离 | 需自行集成 | 需自行集成 |
| 医疗适配能力 | 热词F1: 27→85 | 有限支持 | 有限支持 |
| 部署友好性 | ONNX + Int8量化 + CPU支持 | 较好 | CPU较慢 |

<Block type="info">

**选型结论**：选择FunASR + Paraformer-large。原因不在于某项指标绝对最好，而是它在流程完整、医疗适配、部署友好、上手门槛各方面都够用，放在一条路径上走得通。后续可通过工厂模式方便地切换其他引擎。

</Block>

最终选择了FunASR + Paraformer-large。原因不在于某项指标绝对最好，而是它在流程完整、医疗适配、部署友好、上手门槛各方面都够用，放在一条路径上走得通。特别是它的热词定制能力，对医疗术语识别帮助明显，F1值从27提升到85。而且，由于我们采用了工厂模式，后续可以方便地切换其他引擎。

# 实现过程中的难点与解决

### 难点1：长音频处理

- **问题**：音频>30s可能内存溢出
- **方案**：VAD自动切分
- **参数**：静音>500ms切分，单段≤30s

::right::

### 难点2：说话人分离

- **方案**：集成CAM++模型
- **原理**：声纹特征识别
- **兜底**：交替映射策略
- **状态**：已集成待验证

<Block type="info">

**解决思路**：采用分层处理策略，热词表在识别阶段提升概率。

</Block>
