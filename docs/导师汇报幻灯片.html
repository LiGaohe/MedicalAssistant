中文门诊病历生成系统

基于医患对话的智能问诊助手

汇报人：黎高和

汇报时间：2026年4月

项目阶段：ASR转写模块 + Web应用框架（已完成）

研究背景与目标

研究背景

  • 门诊医生需边问诊边记录病历
  • 注意力分散，问诊效率下降
  • 医疗场景对术语准确性要求高
  • 患者口语化表达，医生专业术语混杂

研究目标

  • 将医患录音自动转写为对话文本
  • 从对话中抽取病历要素
  • 将口语化表达纠正为标准医学术语
  • 生成结构化病历（SOAP格式）

核心问题

  • 提高关键术语的识别率
  • 将ASR错词映射到标准医学术语
  • 抑制幻觉，减少关键事实遗漏
  • 设计适合工程实现的实验方案

调研：国内外研究现状

端到端病历生成

  • SOAP note生成：模块化摘要更稳健
  • MIE、SAFE：医疗对话信息抽取
  • EMRModel：对话映射到结构化病历模板
  • 重点在抽取与生成，术语纠错讨论不足

医疗ASR与术语纠错

  • ASR-EC Benchmark：大模型纠错效果有限
  • Post-decoder biasing：加权词表增强识别
  • DiCODER：词典检索+拼音相似性+受控解码
  • 低频术语识别是系统成败的前置条件

现有研究的不足

中文门诊录音到标准病历的完整系统研究相对分散，模块之间常分别优化，缺少围绕术语准确性的统一设计。 降幻觉研究多面向英文，针对中文门诊口语与录音转写误差的证据约束机制仍不充分。

架构细化：分层架构设计

架构层次

  • 输入层：ASR模块、原始文本
  • 处理层：证据选择、术语规范化、结构化生成、验证
  • 输出层：结构化病历

设计原则

  • 事实来源单一：对话文本为唯一事实来源
  • 分层处理：证据选择 → 术语规范化 → 结构化生成 → 验证
  • 受控术语增强：术语规范化作为受控的第二步

系统设计：ASR模块架构

设计模式

  • 工厂模式 + 策略模式
  • ASRBase定义统一接口
  • 具体引擎实现转写逻辑
  • ASRFactory统一管理创建

设计原则

  • 单一职责：每个引擎专注一种模型
  • 开闭原则：扩展无需修改现有代码
  • 依赖倒置：依赖抽象接口

扩展性优势

  • 继承ASRBase实现新引擎
  • 通过Factory注册
  • 修改配置即可切换
  • 便于技术选型验证

为什么这样设计？

ASR技术发展迅速，需要能够快速切换引擎对比效果。工厂模式使得后续接入Whisper或Qwen3 ASR时， 只需实现接口并注册，无需修改业务代码。

ASR技术选型：对比权衡

对比维度 FunASR Qwen3 ASR Whisper
中文识别准确率 AISHELL-1: 1.95% AISHELL-2: 2.71% zh WER: ~13.8%
流程完整性 VAD + 标点 + 热词 + 说话人分离 需自行集成 需自行集成
医疗适配能力 热词F1: 27→85 有限支持 有限支持
部署友好性 ONNX + Int8量化 + CPU支持 较好 CPU较慢

选型结论

选择FunASR + Paraformer-large。原因不在于某项指标绝对最好，而是它在流程完整、医疗适配、 部署友好、上手门槛各方面都够用，放在一条路径上走得通。后续可通过工厂模式方便地切换其他引擎。

实现过程中的难点与解决

难点1：医疗术语识别率低

  • 问题：药名、病名识别不准确
  • 方案1：热词表提升概率
  • 方案2：规则+拼音纠错

难点2：长音频处理

  • 问题：音频>30s可能内存溢出
  • 方案：VAD自动切分
  • 参数：静音>500ms切分，单段≤30s
  • 效果：控制显存占用

难点3：说话人分离

  • 方案：集成CAM++模型
  • 原理：声纹特征识别
  • 兜底：交替映射策略
  • 状态：已集成待验证
