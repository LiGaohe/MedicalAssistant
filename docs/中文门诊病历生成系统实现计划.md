## 中文门诊病历生成系统实现计划

本计划面向本科项目落地，默认前端采用 funASR，系统目标是从中文门诊录音出发，生成带证据回链的结构化病历草稿。实现策略采用渐进式流水线，而不是一步到位做端到端生成。这样更符合自动书记系统的工程经验 \[1\]，也更适合中文医疗对话任务当前较成熟的抽取优先路线 \[2\], \[3\], \[4\], \[5\]。

本计划不再讨论各模块“选什么”，而是直接给出“先做什么、怎么拆、每阶段交付什么、怎么验收”。默认采用上一份模块对比报告里的最稳妥本科版方案。

## 一期目标

一期系统只解决一个清楚的问题：

- 输入一段中文门诊录音
- 输出一份结构化病历 JSON
- 关键字段保留证据片段
- 对高风险字段做基础规则校验
- 支持人工查看和修改

一期不追求临床直接可用，也不追求全自动闭环。系统定位是病历草稿生成与审核辅助，这与早期 automated medical scribe 的定位一致 \[1\]。

## 一期范围

| 项目 | 一期是否覆盖 | 说明 |
|:---|:---|:---|
| 中文普通门诊单次问诊 | 是 | 主场景 |
| 长音频切分与转写 | 是 | 由 funASR 前端负责 |
| 说话人相关处理 | 是 | 先用 funASR 内能力，必要时保留外接升级口 |
| 术语纠错与规范化 | 是 | 先做词典召回加排序 |
| 病历结构化抽取 | 是 | 先做抽取加槽位填充 |
| 主诉与现病史润色 | 是 | 轻量生成 |
| 证据回链 | 是 | 关键字段必须带 evidence |
| 自动错误检测与自动改写 | 否 | 放到二期 |
| 端到端大模型直出病历 | 否 | 放到二期 |
| 真正 HIS 对接 | 否 | 一期只导出 JSON 和展示页面 |

## 系统总架构

### 数据流

``` text
门诊录音
  -> 音频预处理
  -> ASR 转写结果
  -> 证据选择
  -> 术语纠错与规范化
  -> 病历要素抽取
  -> 槽位填充与轻量生成
  -> 规则校验
  -> 结构化病历 JSON
  -> 人工审核界面
```

### 服务拆分

| 服务 | 职责 | 输入 | 输出 |
|:---|:---|:---|:---|
| audio service | 上传、存储、任务分发 | 音频文件 | 音频任务 |
| asr service | funASR 转写与切段 | 原始音频 | turn 级文本 |
| evidence service | 选出字段相关证据片段 | turn 文本 | 候选 evidence |
| terminology service | 术语纠错与标准化 | evidence 与 ASR 文本 | 标准术语候选 |
| extraction service | 提取症状、检查、诊断等字段 | 规范化文本 | 结构化字段 |
| emr service | 槽位填充与文本润色 | 结构化字段 | 病历 JSON |
| validation service | 规则校验与风险标记 | 病历 JSON | 审核标记后的 JSON |
| review ui | 展示证据与人工修订 | 病历 JSON | 最终导出结果 |

这种拆法和模块化 clinical note generation 的思路一致 \[6\]。每一层都可以单独替换，后面要换抽取模型或补外部 diarization 都不会伤到整条链路。

## 数据结构设计

### 核心对象

| 对象 | 作用 | 关键字段 |
|:---|:---|:---|
| visit | 一次门诊任务 | visit_id, audio_path, status |
| transcript_turn | 一条对话轮次 | turn_id, speaker, start_ms, end_ms, text, confidence |
| evidence_span | 可引用证据片段 | field_name, turn_id, quote, score |
| normalized_term | 规范化术语结果 | source_text, normalized_text, term_type, score |
| extracted_item | 抽取出的结构化项 | item_type, item_name, status, evidence_refs |
| emr_record | 病历结果 | visit_id, emr_json, version, review_status |

### 病历 JSON 最小 schema

``` json
{
  "visit_id": "string",
  "patient": {
    "gender": "男|女|未知",
    "age": "string"
  },
  "chief_complaint": {
    "text": "string",
    "evidence": []
  },
  "history_present_illness": {
    "summary": "string",
    "symptoms": []
  },
  "past_history": {
    "diseases": [],
    "surgeries": [],
    "allergies": [],
    "medications": []
  },
  "examinations": [],
  "assessment": {
    "preliminary_diagnosis": []
  },
  "plan": {
    "medications": [],
    "tests": [],
    "follow_up": [],
    "lifestyle_advice": []
  },
  "quality_flags": {
    "asr_risk": "low|medium|high",
    "validation_errors": [],
    "needs_human_review": true
  }
}
```

## 各模块实现方案

## 音频预处理与 ASR

### 一期实现

- 使用 funASR 完成音频切分、VAD、ASR、标点恢复和说话人相关处理
- 每轮输出 turn 级文本，保留开始时间、结束时间、speaker 和 confidence
- 统一转成内部 transcript_turn 结构

### 输入输出

| 输入            | 输出            |
|:----------------|:----------------|
| wav 或 mp3 音频 | turn 列表       |
| 原始录音元数据  | 结构化转写 JSON |

### 验收标准

- 能稳定处理单次门诊长音频
- 能输出 turn 级文本而不是整段长文本
- 能为后续 evidence 模块提供时间戳和 speaker 信息

### 升级口

- 若说话人错误较多，外接 pyannote \[7\]
- 若时间戳不够准，补 WhisperX 风格切段和对齐 \[8\]

## 证据选择模块

### 一期实现

采用两级策略。

第一层是规则筛选：

- 按 speaker 过滤
- 按症状、检查、药物、诊断触发词筛句
- 按问答模式识别主诉和现病史相关 turn

第二层是轻量打分：

- 依据关键词命中数
- 医患角色
- turn 长度
- confidence
- 与字段词表的相似度

输出每个字段的前若干条候选 evidence。

### 为什么先这样做

noteworthy utterance 研究说明，先筛掉大部分无关内容，可以显著提升后续抽取表现 \[9\]。但一期不必直接训练复杂证据分类器，先用规则加打分就足够。

### 输入输出

| 输入                 | 输出                     |
|:---------------------|:-------------------------|
| transcript_turn 列表 | field 对应 evidence 列表 |

### 验收标准

- 主诉、现病史、既往史、检查、诊断建议等字段都能输出候选证据
- 每个关键字段至少保留 1 到 3 条 evidence
- 无关寒暄内容能被明显压缩

## 术语纠错与规范化模块

### 一期实现

采用 recall and rank 两阶段。

第一步是候选召回：

- 从症状词表、检查词表、药物词表、诊断词表中召回候选
- 召回特征包括字面匹配、编辑距离、拼音相似、同义词映射

第二步是候选排序：

- 结合上下文字段信息打分
- 输出 top 1 标准术语和 top k 候选

这一设计直接对齐中文术语规范化的主流路线 \[10\]，也为后续受限纠错留接口 \[11\]。

### 词表建设

| 词表     | 来源建议                           |
|:---------|:-----------------------------------|
| 症状词表 | 中文常见门诊症状整理加公开医学词表 |
| 检查词表 | 常规化验和影像检查名称             |
| 药物词表 | 常见通用名和商品名映射             |
| 诊断词表 | 门诊高频疾病名和标准写法           |

### 输入输出

| 输入                     | 输出             |
|:-------------------------|:-----------------|
| evidence 文本，turn 文本 | 规范化术语列表   |
| 原始术语 span            | top k 候选及分数 |

### 验收标准

- 可识别常见口语症状到标准术语的映射
- 常见 ASR 近音错词能在候选集中被召回
- 结果中同时保留 source_text 和 normalized_text

### 升级口

- 加入受限解码纠错 \[11\]
- 对复杂诊断短语加入重构式规范化 \[12\]

## 病历要素抽取模块

### 一期实现

采用抽取加槽位填充，而不是直接生成整份病历。

抽取字段包括：

- 性别 n- 年龄
- 主诉相关症状
- 现病史中的症状、持续时间、诱因、伴随症状
- 既往史
- 检查项目与状态
- 初步诊断
- 处理建议

一期实现可以从规则加分类混合做起：

- 年龄、性别用规则抽取
- 症状、检查、诊断、建议用候选项匹配或分类抽取
- 状态标签参考 MIE 的思路设计 present、absent、suggested、unknown 等 \[2\]

### 为什么这样做

中文医疗对话的成熟路线就是先抽结构化项，再写病历 \[2\], \[3\], \[4\], \[5\]。这比直接自由生成更可控，也更适合本科项目调试。

### 输入输出

| 输入                            | 输出            |
|:--------------------------------|:----------------|
| evidence，规范化术语，turn 文本 | extracted_items |

### 验收标准

- 重点字段能输出结构化项而非纯文本段落
- 每个抽取项都能关联 evidence_refs
- 状态标签至少覆盖 present、absent、suggested、unknown

### 升级口

- 参考 CMUI 换成更强的多轮推理抽取 \[5\]
- 参考 SAFE 加强 speaker aware 能力 \[3\]

## 病历生成模块

### 一期实现

这一层只做两件事：

- 将 extracted_items 映射进固定 JSON schema
- 对主诉和现病史做轻量模板化生成

建议策略：

- 主诉由核心症状加时长模板生成
- 现病史由症状列表按时间顺序拼接生成
- 诊断和建议只复述医生明确表达内容

### 为什么不直接上大模型直出

直接结构化生成更适合二期。EMRModel 说明这条路是可行的 \[13\]，但它默认输入更干净，一期如果前面链路还没稳住，直接上大模型只会让错误难排查。

### 输入输出

| 输入            | 输出     |
|:----------------|:---------|
| extracted_items | emr_json |

### 验收标准

- 能稳定输出合法 JSON
- 核心字段不为空或明确留空
- 主诉、现病史具备可读性
- 关键字段均可回链到证据

## 验证模块

### 一期实现

验证模块采用规则校验，不做复杂自动改写。

校验项包括：

- 必填字段是否缺失
- 证据字段是否为空
- 值域是否合法
- 诊断 certainty 是否缺失
- 建议字段是否无依据生成
- 年龄性别等基础字段是否冲突

输出 validation_errors 和 needs_human_review 标记。

### 为什么要单独做

临床 note generation 的问题常常是遗漏和事实错误，而不是文本不通顺 \[14\], \[15\]。一期哪怕只做规则校验，也比完全没有验证层更稳。

### 输入输出

| 输入     | 输出               |
|:---------|:-------------------|
| emr_json | validated_emr_json |

### 验收标准

- 能识别空字段、缺证据、值域错误和明显冲突
- 能输出错误列表供人工审核

### 升级口

- 引入 checklist 人评协议 \[16\]
- 引入错误检测与纠正模块，参考 MEDEC 的检测、定位、改写三步 \[17\]

## 开发阶段安排

## 第 1 阶段 先跑通最小链路

时间建议：第 1 到 2 周

目标：

- 定义 schema
- 跑通音频上传到 turn 文本
- 保存 transcript_turn

交付物：

- 数据库表初版
- 病历 JSON schema
- funASR 接口封装

验收：

- 任意一段测试音频都能产出 turn 级转写结果

## 第 2 阶段 完成结构化抽取主干

时间建议：第 3 到 5 周

目标：

- 完成 evidence 筛选
- 完成术语规范化原型
- 完成字段抽取与槽位填充

交付物：

- evidence service
- terminology service
- extraction service
- emr service

验收：

- 从一段转写文本能生成完整病历 JSON 草稿

## 第 3 阶段 加入验证与审核

时间建议：第 6 到 7 周

目标：

- 完成 validation service
- 完成审核界面
- 支持人工修改和导出

交付物：

- 审核页原型
- validation_errors 输出
- version 管理

验收：

- 人工可以根据 evidence 修改病历并导出最终版本

## 第 4 阶段 做评测与误差分析

时间建议：第 8 到 10 周

目标：

- 建一小批测试集
- 做分层指标评测
- 做错误分类

交付物：

- 指标脚本
- 错误分析表
- 样例展示

验收：

- 能报告转写层、术语层、抽取层、病历层四类结果

## 一期评测方案

| 层级   | 指标                         | 说明               |
|:-------|:-----------------------------|:-------------------|
| 转写层 | CER，关键词召回率            | 重点看医学关键词   |
| 术语层 | 规范化准确率，top k 命中率   | 看候选是否召回对   |
| 抽取层 | 字段级 Precision，Recall，F1 | 看结构化项是否抽对 |
| 病历层 | 字段完整率，人工可接受率     | 看是否能用作草稿   |
| 审核层 | 平均人工修改次数             | 看是否真能减负     |

如果时间允许，后续再加 checklist 式人工评测 \[16\]，这样比单看 ROUGE 更贴近可用性 \[14\], \[15\]。

## 一期数据准备建议

### 最小样本集

一期不需要很多数据，但需要一批高质量样本。

建议至少准备：

- 20 到 50 条测试录音
- 每条录音对应人工转写
- 每条录音对应参考病历 JSON
- 每个核心字段至少标一条证据

### 标注优先级

| 优先级 | 内容                           |
|:-------|:-------------------------------|
| 高     | 主诉，现病史，检查，诊断，建议 |
| 中     | 既往史，用药史，过敏史         |
| 低     | 家族史，婚育史，生活方式细节   |

## 风险与规避

| 风险           | 表现               | 应对                                     |
|:---------------|:-------------------|:-----------------------------------------|
| ASR 误识别传播 | 后面字段全错       | 保存 confidence 和原始转写，保留人工审核 |
| 术语词表太弱   | 规范化命中率低     | 先收缩到高频门诊术语                     |
| 抽取标签过多   | 模型难收敛         | 一期只做核心字段                         |
| 生成幻觉       | 建议或诊断凭空出现 | 严格要求 evidence，规则校验拦截          |
| 系统过重       | 一期做不完         | 不上端到端大模型主干                     |

## 二期升级方向

一期做稳后，二期可以沿三条线升级。

- 音频侧：补 pyannote 或对齐增强 \[7\], \[8\]
- 术语侧：加入受限解码纠错 \[11\]
- 生成侧：引入 LoRA 微调开源大模型做结构化直出 \[13\]

这三条升级线彼此独立，不需要推倒重来。

## 最终建议

这套实现计划的核心，不是把每个模块都做到最强，而是让系统尽快具备三种能力：

- 能从录音稳定走到结构化病历草稿
- 能把关键字段回链到原始证据
- 能通过验证和人工审核把错误拦住

对本科项目来说，这比直接追求一个全能大模型更现实，也更容易形成完整毕业设计闭环。后面如果你愿意，可以在这份计划基础上继续细化成开发清单、数据库表设计，或接口文档。
